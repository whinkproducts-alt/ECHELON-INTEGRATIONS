1. EXECUTIVE SUMMARY
-------------------------------------------------------------------------------
The packages are well structured, but as delivered they will not run end to end,
and several security controls claimed as done are not enforced. The README status
table ("all checkmarks") overstates reality.

Top issues, most serious first:

 1. Authorization bypass: a grantId is never checked against the calling agent or
    the tool (invoke.ts). Any agent holding any grant ID can call any tool.   [C-1]
 2. Remote code execution path: any logged-in session can register a stdio
    provider with an arbitrary command; /discover then spawns it on the server. [C-2]
 3. Tool hijack: discovery upserts Tool by globally-unique name and re-points it
    to the new connector, silently moving existing grants to an attacker's
    endpoint.                                                                   [C-3]
 4. The Integration Hub UI cannot work: every call goes to /api/v1/v1/...       [VERIFIED] [H-1]
 5. Real-time events never fire: NOTIFY with a bind parameter is a Postgres
    syntax error; the failure is swallowed.                                     [VERIFIED] [H-2]
 6. Host recovery is broken: after a Mac comes back, its providers are never
    re-enabled. A host that beats exactly on interval also flaps DEGRADED.      [VERIFIED] [H-3]
 7. The code extractor cannot extract either package (0 of 61 file headers match). [VERIFIED] [H-4]
 8. Credentials are encrypted but never decrypted or sent: E4a-05 is
    storage-only. README says "per-host" keys; code uses one global key.        [H-5]
 9. invoke speaks a different protocol (REST /mcp/tools/call) from discovery
    (JSON-RPC). stdio providers cannot be invoked at all. Real MCP servers
    will not work.                                                              [H-6]
10. Listener leaks pooled connections (max 2); after two SSE connect/disconnect
    cycles NOTIFY and new subscribers hang forever, which can hang invokeCapability. [H-7]

Positive: schema design is sensible; deny-by-default and audit-on-deny pattern is
good; token/ticket hashing for SSE tickets is correct; cloud-spend guard exists
at two layers; test intent (T1-T11) maps well to the controls.

=== CRITICAL ===

C-1  Grant is not bound to the caller or the tool  [READING]
  File: packages/capability-gateway/src/invoke.ts (step 5)
  When grantId is supplied the code does db.capabilityGrant.findUnique({id}) and
  then checks only revokedAt/expiresAt. It never checks grant.subjectType/
  subjectId === agent, grant.capabilityId === tool.id, grant.connectorInstallId,
  grant.hostId, grant.executionPlanId, or grant.scopes.
  Impact: agent B can pass agent A's grant ID for a different, more sensitive tool
  and succeed. All of T1-T11 pass a valid grantId for the matching pair, so no test
  catches this. Scopes and plan-scoped (mission-scoped) grants exist in the schema
  but are never enforced anywhere.
  Also: the no-grantId branch uses findFirst without filtering expiresAt, so it can
  pick an expired grant while a valid one exists (false deny). policy.ts does this
  correctly.
  Fix: after loading the grant, require subject match + capability match (+
  connector/host/plan if set) + scope check; add a negative test "agent B with
  agent A's grantId is denied".

C-2  Arbitrary command execution via provider registration  [READING]
  Files: integrations/[...path]/route.ts (POST providers, discover), mcp-client.ts
  POST /providers stores body.command and body.args unvalidated. POST
  /providers/:id/discover calls McpClient.connect, which does spawn(command, args)
  on the web server with the server's privileges. There is no role check (any valid
  session), no command allowlist, and the egress firewall in egress-firewall.sh only
  covers uid 1954 (echelon-plugin), not the web server user.
  Impact: any session token = shell on the app host.
  Fix: restrict stdio to hosts (run on the Mac/remote worker, not in the web
  process); require founder role; allowlist command binaries; run as the sandboxed
  plugin uid; never spawn from a web request handler.

C-3  Tool name hijack on discovery  [READING]
  File: integrations route (discover). Tool.name is globally @unique. Upsert's
  update branch sets connectorInstallId = the new connector. Grants reference
  tool.id, so registering a second provider that advertises a tool with the same
  name moves every existing grant for that tool to the new endpoint.
  Impact: an untrusted provider can capture traffic meant for a trusted one.
  Fix: make the tool identity (connectorInstallId, name) unique; never update
  connectorInstallId on conflict; fail loudly on a name collision.

=== HIGH ===

H-1  Integration Hub UI calls the wrong URL  [VERIFIED]
  File: apps/web/src/app/integrations/page.tsx. api() prefixes '/api/v1', and every
  caller passes a path starting '/v1/...', giving /api/v1/v1/integrations/... (404).
  Every fetch in the page fails. Fix: drop one '/v1'.

H-2  NOTIFY is never delivered  [VERIFIED]
  File: apps/web/src/lib/listener.ts: pool.query(`NOTIFY "ch", $1`, [payload]).
  I reproduced this against PostgreSQL 16 with the extended protocol: ERROR syntax
  error at or near "$1". NOTIFY does not accept bind parameters. invoke.ts wraps
  it in try { } catch { /* listener optional */ }, so the failure is silent and the
  SSE stream never receives live events. Fix: SELECT pg_notify($1, $2) (works,
  verified). Also stop swallowing the error silently; log it.

H-3  Host recovery and DEGRADED flapping  [VERIFIED by simulation]
  Files: heartbeat/route.ts, host-runner.ts, state-machine.ts
  a) The heartbeat route writes status='ONLINE' directly. host-runner only
     re-enables providers when evaluateHostState reports a transition to ONLINE
     with the stored status OFFLINE. After a heartbeat, stored status is already
     ONLINE, so no transition is reported and the providers disabled during the
     outage stay DISABLED forever. Simulation: transition=null after heartbeat.
  b) The re-enable query flips EVERY DISABLED connector on the host to ENABLED,
     including ones the Founder disabled on purpose. There is no marker for
     "disabled by outage".
  c) Defaults: interval 30s, degraded after 30s. A host beating exactly every 30s
     is DEGRADED on every cycle (simulation: 10 of 10 cycles). Policy requires
     host.status === 'ONLINE', so DEGRADED blocks invocations. Use degraded >= 2x
     interval (e.g. 75s) and offline >= 3x (e.g. 120s).
  d) T8-T10 do not test recovery, so none of this is caught.
  Fix: move recovery into one place (the runner or a shared applyHeartbeat that
  also re-enables), record "disabledReason: HOST_OFFLINE" on the connector and
  re-enable only those; fix thresholds; add a test "Mac returns -> providers back".

H-4  The extractor cannot extract either package  [VERIFIED]
  File: scripts/extract-code-package.py. Its regex expects lines of '=' and a bare
  'FILE:'; the packages use lines of '#' and '# FILE:'. Result: 0 matches in PKG-A
  (25 headers present) and 0 in PKG-B (36 present). The script prints "no FILE:
  markers found". README's step 1 therefore fails.
  Related: PKG-B's header says "34 total" but contains 36. Both packages contain
  invoke.ts and the extractor; extracting PKG-B after PKG-A silently reverts
  invoke.ts to the version WITHOUT the NOTIFY call. tsconfig.paths.json is not
  valid JSON when extracted (contains '#' comment lines and trailing notes).
  Fix: regex ^#{10,}\n# FILE:\s*(\S+)\n#{10,}\n; refuse to overwrite an existing
  file without --force; ship one merged package.

H-5  Credential isolation is storage-only; README overstates it  [READING]
  - decrypt() is never called anywhere. McpClient never receives credentials
    (hostHeader unused); invoke.ts sends no Authorization header. A provider that
    needs a token cannot be called.
  - README says "AES-256-GCM, per-host". crypto.ts uses one global ENCRYPTION_KEY,
    no key ID/version (no rotation), no per-host derivation.
  - Audit rows store raw inputSummary/outputSummary (1000 chars) with no
    redaction, so secrets or founder-private text in tool I/O land in the Action
    table in clear text.
  - credentialHint stores the last 4 chars (leaks the whole value if short).
  Fix: decrypt at call time inside the gateway only; derive per-host keys (HKDF) or
  document single-key as accepted; version the ciphertext; add redaction.

H-6  Protocol mismatch: discovery vs invocation  [READING]
  McpClient (discover) speaks JSON-RPC to the endpoint. invoke.ts POSTs a custom
  REST body to new URL('/mcp/tools/call', endpoint) (which also discards any path
  in the endpoint). The test mock implements the custom REST path, so tests pass
  while a real MCP server (JSON-RPC at /mcp) would 404/400. stdio providers have no
  endpoint, so invoke throws "no endpoint": stdio tools are discoverable but not
  invocable. Also: JSON-RPC "error" and MCP result.isError are treated as success.
  McpClient gaps: no notifications/initialized after initialize (spec requires it);
  res.json() fails if a server answers with SSE (the Accept header offers it);
  stdio requests have no timeout (hang forever); responses are matched by id with
  no check on `method`, so a server-initiated request can be mistaken for a reply;
  protocolVersion is 2024-11-05.
  Fix: one transport layer (McpClient) used by BOTH discover and invoke, behind
  allowlistedFetch.

H-7  Listener connection leak can hang invocations  [READING]
  File: listener.ts. Pool max=2. Each first subscription checks a client out with
  pool.connect() and never releases it or UNLISTENs. When the last subscriber
  leaves, the channel is forgotten, so the next subscriber checks out another
  client. After two SSE connect/disconnect cycles both pool slots are held;
  notify() (pool.query) and further subscribers wait forever (no connection
  timeout). invoke.ts awaits notify() after the Action is saved, so invokeCapability
  itself can hang after succeeding. In dev the module-level Pool is also recreated
  on hot reload (no globalThis guard, unlike db.ts).
  Fix: one dedicated long-lived LISTEN client for the process; reference-count
  subscribers; separate pool for notify; connectionTimeoutMillis; globalThis guard.

H-8  Egress control has holes  [VERIFIED where noted]
  a) allowlistedFetch follows redirects by default: an allowlisted host can 302 to
     a non-allowlisted host. Needs redirect:'manual' (or 'error') and re-checking.
  b) DNS rebinding: the IP check resolves the name, then fetch() resolves again
     (time-of-check/time-of-use). The comment "defeats DNS rebinding" is not true.
     Also if the hostname is allowlisted the IP is never checked, so an allowlisted
     name pointing at 169.254.169.254 or RFC1918 passes.
  c) mcp-client.ts uses raw fetch and is exempt from the lint rule; the discover
     route therefore makes unrestricted outbound requests to a user-supplied URL
     (SSRF to cloud metadata, internal services).
  d) extractUrls  [VERIFIED]: only strings that are entirely a URL are caught.
     Missed: URL inside a sentence, scheme-less hosts, URLs nested deeper than 6
     levels, URLs in object keys. False positives: "note:todo", "time: 10:30" and
     "C:\Users\x" all parse as URLs with an empty host and are DENIED.
  e) hostAllowed  [VERIFIED]: "0.0.0.0/0" allowlists everything (no registration
     validation); "a.test:80" never matches http://a.test:80/ (URL drops default
     ports); IPv6 literals never match (hostname keeps brackets, isIP=0); entries
     are case-sensitive.
  f) scripts/egress-firewall.sh: Linux iptables only (your Founder host is a Mac:
     needs pf); no ip6tables (IPv6 unrestricted); DNS to any resolver allowed (DNS
     tunnelling channel); applies only to uid 1954, not to the gateway or web
     process; allowlist file takes IPs only. README claims "kernel + application
     egress" as done; kernel layer is not wired to the process that makes calls.

H-9  Cost-class guard is bypassable  [READING]

  UI and API have no way to set them. A cloud-billable tool registered through the
  Hub is FREE, so BUDGET_CLOUD_DISABLED never fires for it. riskClass is never read
  by policy or invoke (no approval/confirmation by risk). requiresEgress and
  schema 'permissionClass'/'confirmationMethod' fields are also unused.

=== MEDIUM ===

M-1  policy.ts is not the single decision point (README claim)  [READING]
  invoke.ts re-implements the gates inline and never calls decide(). policy.ts
  omits the founder-private and egress checks that invoke.ts has. The two will
  drift. Actions DISABLE_PROVIDER and REVOKE_GRANT are typed but unhandled; the
  routes for disable, revoke, review, discover never consult policy. ENABLE_PROVIDER
  does not check the user's role (GRANT does). Any authenticated user can revoke any
  grant by ID (no ownership check on DELETE /grants/:id) and read any provider's
  tools.

M-2  "Review permissions" is a button, not a review  [READING]
  Review flips status to REVIEWED with no displayed permissions, no tool list, no
  egress summary, no automated checks, and is allowed before Discover. The same user
  registers, reviews and enables (no separation of duties). Enabling a provider with
  zero discovered tools is possible. README op (c) is therefore only nominally met.

M-3  Failed invocations are not audited  [READING]
  Only PolicyError is persisted. Network failures, timeouts (AbortError) and
  "MCP call failed: 500" are rethrown with no Action row, so a failed call leaves
  no trace. Also the Action is written AFTER the side effect (no write-ahead
  "intent" record), so a DB failure after a successful call loses the audit, and
  the grant counter update can throw after the audit row exists. Denial rows omit
  connectorInstallId/capabilityId/hostId so a denial cannot be attributed to a tool.
  persona, planId, executionPlanId and correlationId are never populated.

M-4  Founder-private guard is a label check, not a control  [READING]
  Only input.__marker === 'FOUNDER_PRIVATE' at the top level is blocked. Nested,
  differently-cased, or unmarked founder data passes. Nothing connects the seed's
  founder-private roster row (domain 'founder-private' in agent_knowledge) to any
  access check. T11b proves only that the literal marker is rejected.

M-5  Output/input validation is a stub  [READING]
  Result check is "is an object" (code comment says ajv is to be wired). Input is
  never validated against inputSchema; outputSchema for discovered tools is a
  hard-coded {type:'object'}.

M-6  Realtime event stream issues  [READING]
  - Replay then subscribe leaves a gap (events committed between the two are lost);
    subscribe first and buffer.
  - EchelonEventStream.onmessage only fires for unnamed events; events are sent with
    "event: <type>", so the cursor is never updated and reconnect does not resume.
  - The subscribe callback is async but listener.ts try/catch cannot catch its
    rejections (unhandled rejection).
  - /events/ticket does not catch the error requireSession throws, so an invalid
    session yields 500 instead of 401. Expired tickets are never purged.
  - The Hub UI polls every 5s instead of using the SSE client it ships with.

M-7  Heartbeat endpoint  [READING]
  One shared WORKER_TOKEN for all hosts: any holder can mark any hostId ONLINE.
  Unknown hostId makes db.host.update throw (unhandled 500). Not constant-time
  compare (hash compare softens this). Runner has no lock, so two runners would
  duplicate audit rows, and it can overwrite a heartbeat that lands mid-cycle
  (self-heals next cycle). A host created ONLINE with lastHeartbeat=null never
  transitions.
